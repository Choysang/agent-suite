# Obsidian-Wiki-LLM

**🌐 English | [中文](README.md)**

> This is not note-taking software. It is a knowledge operating system where the AI is the librarian: humans only drop things in and ask questions; the AI handles summarizing, filing, linking, and freshness. The theoretical basis is Karpathy's LLM Wiki idea: plain RAG re-derives every answer and forgets it; this system compiles each derivation once and keeps reusing it, so knowledge compounds like a snowball.

Inspired by two gists:

- [Andrej Karpathy — LLM Wiki v1](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f): don't treat the LLM as a query engine, treat it as a librarian; raw material is "source code", the LLM continuously compiles it into a structured wiki.
- [rohitg00 — LLM Wiki v2](https://gist.github.com/rohitg00/2067ab416f7bbe447c1977edaaa681e2): adds lifecycle governance — epistemic status, explicit supersession, conflict review.

This project is how those ideas actually run on **Obsidian + Claude Code**, iterated continuously on a real personal knowledge base (now v5). Evolution: v3 turned workflows into six executable slash commands; v4 added experience cards with a globally injected router; v5 unifies the card contract, generates routing from cards, and ships the engine and behaviors as Agent Skills.

## Core idea (one sentence)

**Cards are the only state; routing is generated from cards; judgement belongs to the model, bookkeeping belongs to `kb`.**

- **Cards**: one card per scenario (lesson / playbook / tool / source / note). The frontmatter *is* the routing contract — `when` (when it applies, written as the user's own words or symptoms) and `not_when` (when it doesn't) decide when the card gets retrieved.
- **Routing**: not a hand-maintained directory, but generated by `kb build` from cards plus the taxonomy (`taxonomy.yml`). Only one small table (`ROUTER.md`) lives in the always-on context; you descend into it only when a task matches — the context stays light no matter how big the vault grows.
- **Red lines**: each domain carries one always-visible "red line" in the ROUTER table (e.g. "PS 5.1 has no `&&`", "never treat Excel error values as 0"). Every session sees them — insurance paid for by past mistakes.
- **Evidence grades**: lessons carry `evidence` — measured > decided (the user's call) > external (an article said so) > inferred. Lower evidence never overwrites higher; conflicts are never auto-resolved, they are surfaced for the user to decide.
- **Absorption**: every new knowledge item is first checked with `kb find`, then merged under one of five cases (append / refine / better alternative / conflict / new) so duplicates never pile up.

## Architecture: two worlds + progressive disclosure

**Two worlds**

| World | Directories | Nature |
|---|---|---|
| Workbench | `00.Inbox` `10.Projects` `20.Areas` `40.Archive` `50.Daily` | Working records, not routed, free-form |
| Knowledge | `30.Wiki/` (lessons / playbooks / tools / sources / notes / raw / routes) | The only routed area; cards live only here |

**Four routing layers (progressive disclosure)**

```
L0 ROUTER.md (one table, always in context) → L1 routes/<domain>.md (on match) → L2 the card → L3 raw source (when the card isn't enough)
```

**Action loop**: humans do only two things — drop things in, ask questions. Everything else is five skills:

| Situation | Skill | What it does |
|---|---|---|
| Link / article / clip / pasted text | `capture` | dedupe → read source → judge → write card → extract lessons |
| Pitfall / decision / good practice | `sink` | write a lesson card on the spot, with evidence grade |
| Project or big update wrapping up | `sink retrospective` | write the 8-section project playbook; pitfalls become lesson cards |
| Start of day / todos / quick note | `daily` | auto-generated work log; humans never write it |
| Every 2–4 weeks | `tidy` | clear inbox, merge duplicates, health check |

Behaviors live in Agent Skills (`.agents/skills/*/SKILL.md`) — **rules don't rely on memory, they rely on executable skills**, so they survive session changes, model changes, and agent changes. Bookkeeping runs on a single-file Python engine `kb.py` (PyYAML is its only dependency: BM25 search, card scaffolding, dedupe, validation, route generation).

## How retrieval works

Every answer must walk through:

```
① Match the task against ROUTER.md keywords; only descend on a match
② Open the second-level route, read only the cards you need; raw sources only when cards fall short
③ Synthesize, citing the source card for each key conclusion
④ Anything valuable goes back via sink — the library grows with use
⑤ Honest fallback: say "knowledge gap" when the library has nothing; never pass generic model knowledge off as library content
```

Answers are **traceable** — not invented, but pointable back to specific cards — and you **only read what matched**, decoupling token cost from library size.

## vs. traditional RAG

| Dimension | Plain RAG | This method (LLM Wiki) |
|---|---|---|
| Storage | Vector database | Obsidian Markdown cards |
| Retrieval | Embedding similarity | Generated routing (keywords + red lines) + BM25 over cards |
| Reuse | Re-stitch context every time | Compile once, reuse and absorb forever |
| Readability | Unfriendly to humans (vectors) | Both humans and AIs can read it directly |
| Scale threshold | Needs embedding API + vector DB | Only Claude Code + Python; no vectors for small libraries |

RAG is not rejected — once cards exceed ~500 and routing visibly misses, add local hybrid retrieval (BM25 + vectors) as a supplement.

## Building your own

No need to design from scratch:

1. **Run the bootstrap**: [`BOOTSTRAP.md`](BOOTSTRAP.md) is a paste-ready prompt; answer a few questions and a same-shaped system is built in about 10 minutes.
2. **Make workflows skills, not documentation** — the most overlooked and most important step. Rules written in a doc get "forgotten" after a few sessions; rules made into skills keep executing.
3. **Let git own history** — checkpoints before big changes give the AI confidence to maintain and you confidence to let it.
4. **Start minimal, grow real** — let domains and topics emerge from what you actually capture; don't pre-design dozens of categories.

Common pitfalls:

- **Over-engineering is killer #1** — shallow directories, one copy of the rules, add complexity only when a real need appears
- **`tags` must be a controlled vocabulary** (`taxonomy.yml`) — free-form tags make routing impossible after three months
- **Write `when` in the user's own words** — routing accuracy lives and dies on that line
- **Key conclusions need a source + evidence grade** — the lifeline against confident fabrication
- **Don't jump to vector databases** — routing + index + BM25 is fast and readable
- **Keep human friction at zero** — humans only drop things in and ask questions; once actions get complicated, the system dies

## Quick start

1. Create an empty folder, open it as a vault in Obsidian, and start Claude Code (or any file-capable AI agent) inside it.
2. Open [`BOOTSTRAP.md`](BOOTSTRAP.md) and paste the prompt to the AI.
3. Answer a few questions about yourself (name, focus, your knowledge domains).
4. Day-to-day, all you do: drop things into `00.Inbox/` and say "save this"; say "sink this" when you hit a pitfall; say "daily" to start the day; "retrospective" when a project ends; "tidy" every few weeks.

Full principles in [`GUIDE.md`](GUIDE.md).
