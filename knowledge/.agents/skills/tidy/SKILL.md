# tidy — 整理

规范以 Vault `AGENTS.md` 为准。`kb` = `python .agents/skills/kb/scripts/kb.py`。

1. **收件箱**：`00.Inbox/` 和 `Clippings/` 里的链接、文章、剪藏走 `capture`；工作文件（xlsx、docx 等）移到 `10.Projects/` 或 `20.Areas/`；没价值的列给用户。
2. **合并**：找出上次 tidy 以来新增或修改的卡（`git log --since=<上次 tidy> --name-only -- 30.Wiki`），逐张 `kb find "<summary>"` 找同类，按吸收规则合并；「更优」和「冲突」列给用户拍板。
3. **体检**：`kb build` 把 ERROR 修完。WARN 里超过 180 天没验证的卡，列给用户确认是否仍成立。空主题、含义重叠的主题，提议合并（改 taxonomy 时同步改卡片标签）。
4. **待办**：`50.Daily/TODO.md` 里完成超过 30 天的项，移到 `50.Daily/TODO-done.md`。
5. **收尾**：`git add -- <本次修改的文件> && git commit -m "tidy: <日期>"`，汇报控制在一屏内。

## 受控晋升与退役

1. 排查用 `kb find "相关场景" --include-stale --json`，结合卡片 `read --full` 看误导证据；stale 是待修复/复核，不是自动删卡依据。修复产生新 revision，旧反例仍留档。确实被替代时用现有 superseded 关系，检查双链后再归档。
2. 对 `promotion_ready` 或经过复核的 verified 卡，核对独立任务、证据、适用范围及反例；分数只帮助发现候选。重复护栏合并，已失效规则退役留痕，不只增不删。
3. 普适 lesson 可提炼一句短规则；优先放项目规范或局部 Skill，确有跨项目价值才进入全局 guidelines。稳定多步操作可变成脚本并建 tool 卡。每项提案带现有重复规则、最小 Diff、独立验收任务、上下文/执行成本与回滚方法；已有授权内实施，需新增授权时先准备可审阅结果。
4. 规则/脚本改动先运行相关测试和检索回归，再用未用于设计的真实任务验收；退化则回滚，不改测试答案迎合实现。正文 lint 通过后 build，仅提交本轮文件。机制详见 Vault `RSI.md`。

## 全库整理与内容分配

- 先列清单并保存基线、文件哈希和未提交修改；批量标签迁移先检查全部映射，未覆盖项修正后再写入。原始资料与历史归档保留，不按新卡片预算改写。
- 知识卡片使用 taxonomy 的域/主题；第一个为主归属，跨域标签只保留实际有用的入口。工作台不加入知识路由，可用已登记主题及 `record/` 私有管理标签；避免为工作记录建立空的知识主题。
- 全库整理时检查每张卡片的 summary、when、not_when 与标签；原字段已准确则保留。摘要写可复用结论或资料用途，说明时间和适用范围；未验证排行、营销说法与无实验条件的数字不升级为事实。
- 长笔记先按字节保存到 raw 快照，再整理为短导航或有独立检索价值的专题卡。保留旧文件名与双链、用户原话、原文入口；模型总结不能替代唯一原文。
- 不因整理刷新 verified、evidence 或经验反馈。RSI candidate 表示尚未完成版本反馈晋升，不推翻原有证据等级；保留旧 feedback_log。
- 工作日志补标题、摘要与归属即可；历史已完成项只有可核对的完成日期才能按时限归档。缺附件与不可恢复的历史链接应列明，不创建伪资料或虚构完成状态。
- 修改后运行 lint、check、build，检查原文哈希、关键用户改动和内部链接；试查代表性需求。功能通过不等于召回率或回答质量提升。
- 发布只从通用项目仓库的明确文件清单构建；个人笔记、原文、访问资料与本地整理脚本不进入公开包。
